# 后台切换 AI 上游调用模式（流式/非流式）

## 背景与设计

**现状**：服务端 `ChatCompletion` 强制 `stream=false` 调上游（120s 超时客户端）；Flutter 客户端只调 `/api/v1/chat/completions` 非流式端点，本地模拟打字。`deepseek_service.go` 已有休眠的真实流式实现 `ChatCompletionStream`（写 io.Writer、逐 chunk flush）。

**设计**：新增后台开关 `chat_upstream_stream`（SystemConfig，默认关闭）。开启后，主聊天端点 `/chat/completions` 改用 **流式调上游 + 服务端聚合**：以 `stream=true` + `include_usage` 读上游 SSE，把增量 chunk 聚合回完整 `ChatCompletionResponse`，计费结算后返回与现在**完全相同**的 JSON。客户端契约不变。

**收益**：流式上游连接持续有数据流动，长回复（尤其思考模式）不易触发 120s 非流式空闲超时（改用 300s 流式客户端）；某些网关对两种模式行为不同，管理员可切换规避。

**范围界定**：
- 只改主端点 `ChatCompletions` 的上游调用方式；`/chat/completions/stream` 旧端点保持现有传输兼容行为不动
- 记忆 AI / 画像 AI 等客户端发起的调用都走同一端点，自动受益
- admin 后台网络审核等服务端内部调用保持非流式

## 改动文件

### 1. `services/chat_stream_config.go`（新建）
仿 `maintenance_service.go` 模式：
- `ChatUpstreamStreamConfigKey = "chat_upstream_stream"`
- `GetChatUpstreamStreamEnabled() bool`（读 SystemConfig，`"true"` 才开，默认 false）

### 2. `services/deepseek_service.go`：新增 `ChatCompletionViaStream(ctx, req) (*ChatCompletionResponse, error)`
- `resolveUpstream` + `adaptRequestForFormat`（gemini 格式剥离 thinking 参数，与非流式路径一致）+ `Stream=true` + `StreamOptions{IncludeUsage:true}`
- 用 `getUpstreamClients().stream`（300s）+ `Accept: text/event-stream`
- 重试：复用 `upstreamRetryDelay` 重试循环，但**只在尚未收到任何 chunk 时重试**（收到部分内容后重试会导致内容重复）
- SSE 扫描（1MB 行缓冲，同休眠代码），逐 chunk 解析并聚合：
  - `delta.content` / `delta.reasoning_content` 字符串拼接
  - `delta.tool_calls` 按 `index` 聚合（id/type/name 取首次出现，`arguments` 片段拼接）
  - `id/object/created/model/role` 取首 chunk，`finish_reason` 取最后非空值
  - `usage` 取最终 usage-bearing chunk
- 截断（scanner 错误）：返回部分用量估算 + error（handler 走现有释放预留路径）
- 上游未返回 usage：零 token + 日志（同休眠代码）

### 3. `handlers/chat.go`
- `chatCompletionService` 接口加 `ChatCompletionViaStream` 方法
- `ChatCompletions` handler 构建完 `dsReq` 后分支：
  ```go
  if services.GetChatUpstreamStreamEnabled() {
      result, err = h.deepseekService.ChatCompletionViaStream(ctx, dsReq)
  } else {
      result, err = h.deepseekService.ChatCompletion(ctx, dsReq)
  }
  ```
  计费结算/响应格式不变

### 4. `handlers/admin.go`：`GetChatStreamConfig` / `UpdateChatStreamConfig`
仿维护模式配置：GET 返回 `{enabled}`，PUT 校验后 `SaveSystemConfig` + 审计日志 + `SuccessMsg`（中文消息，与该文件现有风格一致）

### 5. `routes/routes.go`
adminGroup 注册 `GET/PUT /admin/chat-stream-config`

### 6. `admin/index.html`：新卡片"🌊 AI 上游调用模式"
位于维护模式卡片之后：checkbox"启用流式调用上游"+ 说明文案（开启后 SSE 流式读取上游响应、长回复不易超时；客户端接口格式完全不变）+ 保存按钮

### 7. `admin/js/app.js`
`loadChatStreamConfig()` / `saveChatStreamConfig()`（GET/PUT `/admin/chat-stream-config`），注册到 `case 'config':` loader

### 8. 测试
- 更新 3 个现有 handler 测试 mock（`chat_nonstream_test.go` 的 2 个 + `chat_security_test.go` 的 1 个）：补 `ChatCompletionViaStream` 桩实现（委托给各自 ChatCompletion 或返回错误）
- 新增 `services/deepseek_stream_aggregate_test.go`：httptest 假上游发 SSE，验证聚合（内容拼接、tool_calls 参数拼接、usage 提取、截断部分返回、非 200 错误）

### 9. 验证
`go build ./...` + `go test ./...` 全绿后提交推送

## 验收
- 开关默认关闭：行为与现在完全一致（非流式上游）
- 开关开启：上游请求体含 `"stream":true`，客户端响应 JSON 结构不变
- 后台"配置"页出现新卡片，切换即时生效（SystemConfig 热读，无需重启）
